\section{Problem Definition}

Universities are increasingly incorporating \gls{AI} tools into administrative and academic processes as part of broader digital transformation strategies. However, the most capable \glspl{LLM} are typically proprietary and cloud-hosted, which raises concerns around recurring costs, data privacy, and dependency on external infrastructure --- concerns that are particularly relevant for institutions with limited computational resources. This creates a need to evaluate whether smaller, open-source \glspl{LLM}, deployable on modest institutional hardware, can perform reliably on domain-specific \gls{QA} tasks grounded in an institution's own documents, such as course syllabi and program descriptions.

This study benchmarks six open-source \gls{LLM} configurations, spanning two model families (Qwen2.5 and Llama 3.1 at the efficient tier, DeepSeek-R1-Distill across the mid and upper-bound tiers) at multiple parameter scales and quantization levels, using a \gls{RAG} pipeline over a curated set of university postgraduate course documents. Model performance is assessed across three question types (binary, short-answer, and open-ended), with the goal of identifying the configurations that offer the best practical balance between answer accuracy and computational efficiency for self-hosted deployment at the university.

\section{Experimental Design}

\subsection{Dataset}

The QA dataset consists of 270 questions in Spanish (90 per category: binary, short-answer, open-ended), each labeled with its source course and program (\textit{Maestr\'ia}) and a curated expected answer. Each of the 90 questions per category is evaluated exactly once per model per context-supply condition (Section~\ref{ssec:context-conditions}), using greedy (deterministic, \texttt{do\_sample=False}) decoding throughout, rather than repeated sampled batches --- an earlier design considered drawing random 20-question batches per run to estimate variance across samples, but was dropped in favor of evaluating the full 90-question set once per condition, given the project timeline.

The retrieval/context corpus consists of 15 university postgraduate course-program documents (PDF and DOCX, in Spanish), covering course descriptions, objectives, evaluation structure, and bibliography. Each document is converted to plain text with a custom extractor that walks paragraphs and tables in document order (\texttt{python-docx}'s default paragraph-only traversal misses table content entirely, and all 15 source documents store their content inside tables) and preserves list structure, including nested bullets, via each paragraph's \texttt{numPr}/\texttt{ilvl} properties.

Because a raw question (e.g. \textit{``\textquestiondown Es la asistencia obligatoria?''}) does not identify which of the 15 courses it refers to, each question is composed with its course and program before being sent to a model: \textit{``En el curso \{Curso\} de la \{Maestr\'ia\}, \{Pregunta\}''}. A category-specific instruction is appended to the composed question, so that binary and short-answer questions are not padded with unneeded elaboration that would hurt exact-match-style scoring, while open-ended questions are explicitly invited to elaborate: \textit{``Responde \'unicamente con `S\'i' o `No'.''} (binary); \textit{``Da una respuesta breve y directa, en una sola frase.''} (short-answer); \textit{``Da una respuesta completa y explicativa.''} (open-ended).

\subsubsection{Context-supply conditions}
\label{ssec:context-conditions}

Every question is answered under two context-supply conditions, using an otherwise identical prompt template, so the only variable between them is how context is supplied:

\begin{itemize}
  \item \textbf{RAG}: the 15 documents are split into $\sim$500-word chunks (50-word overlap). Each chunk's embedded text is prefixed with its source document's title before embedding (\textit{``[Documento: \ldots]''}), since the source documents share near-identical boilerplate structure across courses (e.g. \textit{``Asistencia: Obligatoria''}) that would otherwise embed indistinguishably regardless of course. Chunks are embedded with \texttt{paraphrase-multilingual-MiniLM-L12-v2} and indexed with FAISS (cosine similarity via normalized inner product). Retrieval returns the top 5 chunks for the composed question, capped at 2 chunks per source document, so a single verbose document cannot crowd out all 5 slots with its own near-duplicate chunks.
  \item \textbf{Full-context}: the entire 15-document corpus ($\sim$17K words, $\sim$24K estimated tokens) is concatenated (each document labeled the same way as the RAG chunk prefix) and included in every prompt, in place of retrieved chunks. Feasible here because the corpus is small relative to all benchmarked models' context windows, with one exception: Qwen2.5-3B-Instruct's default configuration caps at 32{,}768 tokens (despite being marketed with a 32K--128K range, which requires explicit RoPE-scaling configuration not used here), close enough to the corpus-plus-prompt size to occasionally trigger a context-length warning; results for this model under the full-context condition should be read with that caveat.
\end{itemize}

Both conditions were run to completion for all 6 benchmarked models (3{,}240 total question-answer pairs: 270 questions $\times$ 6 models $\times$ 2 conditions), so that RAG and full-context can be compared directly per model and per category, not just in aggregate.

\subsection{LLMs to benchmark}

Models are grouped into three tiers, reflecting the accuracy-vs-efficiency tradeoff central to this study's motivation. All models are loaded from their native (safetensors) Hugging Face repositories and quantized on-the-fly via \texttt{bitsandbytes}, rather than relying on pre-quantized GGUF files, so that a single loading and generation codepath is shared across every configuration.

\begin{itemize}
  \item \textbf{Efficient tier} (target deployment candidates):
  \begin{itemize}
    \item Qwen2.5-3B-Instruct (full precision)
    \item Llama-3.1-8B-Instruct (4-bit)
  \end{itemize}
  \item \textbf{Mid tier}:
  \begin{itemize}
    \item Llama-3.1-8B-Instruct (full precision)
    \item DeepSeek-R1-Distill-Qwen-14B (4-bit)
    \item DeepSeek-R1-Distill-Qwen-14B (8-bit)
  \end{itemize}
  \item \textbf{Upper-bound reference tier} (to quantify what is given up by deploying smaller models):
  \begin{itemize}
    \item DeepSeek-R1-Distill-Qwen-14B (full precision)
  \end{itemize}
\end{itemize}

\subsubsection{Generation settings}

All models generate with greedy decoding (\texttt{do\_sample=False}) for reproducibility, with a 300-token budget per answer. DeepSeek-R1-Distill-Qwen-14B is a reasoning model: by default, its chat template opens a \texttt{<think>} block that the model fills with a chain-of-thought trace before producing a final answer. Pipeline validation showed this reasoning trace added substantial latency (up to $\sim$40s for a single trivial question, such as confirming $2+2=4$) without changing the final answer's content on the validation questions tested. All three DeepSeek-R1-Distill-Qwen-14B configurations therefore run with reasoning explicitly disabled: the \texttt{<think>} block is force-closed immediately after the prompt (appending \texttt{"\textbackslash n\textbackslash n</think>\textbackslash n\textbackslash n"} before generation begins), so the model answers directly. This is a deliberate accuracy-for-latency tradeoff specific to this study's efficiency framing, not a claim that reasoning never helps; it is reported here as part of the experimental design rather than left implicit in the results.

For each configuration, model size (parameters), GPU memory footprint, inference latency, and approximate GPU cost in the current market are reported and compared. Cost is estimated as mean generation time per query multiplied by an hourly GPU rental rate, projected to a cost-per-1000-queries figure; this is not what Kabr\'e itself charges (allocation-based, not billed per hour) but a stand-in for what the same workload would cost on commercial cloud infrastructure --- the actual comparison point for this paper's cost argument against paid, proprietary LLM APIs. The rate used is \$0.96/hr, the on-demand dedicated price for an NVIDIA L40S --- the same GPU model used throughout this study's own infrastructure --- as listed by Spheron Network~\cite{spheron2026l40s}.

\subsection{Infrastructure}

Experiments are run on Kabr\'e, the national HPC cluster operated by Costa Rica's Centro Nacional de Alta Tecnolog\'ia (CeNAT), accessible to CONARE-affiliated universities including the Instituto Tecnol\'ogico de Costa Rica. Jobs are scheduled via Slurm on the \texttt{nukwa} partition family, which provides single-GPU compute nodes: 4 nodes with an NVIDIA Tesla V100 (32GB), and 7 nodes with an NVIDIA Ada L40S (46GB usable VRAM).

\makeatletter
% Loops over \accuracytable, building one tabular row (formatted with
% \pgfmathprintnumber) for every row whose 'category' column equals #1,
% using only the columns listed in #2 (comma-separated, first output
% column is always model_key). Output is accumulated into a macro and
% printed only after the loop's own grouping has closed — emitting
% "&"/"\\" directly from inside \foreach's body breaks tabular's
% alignment parser, hence the two-step accumulate-then-print structure.
\newcommand{\FilterByCategory}[2]{%
  \gdef\FBC@accum{}%
  \pgfplotstablegetrowsof{\accuracytable}%
  \pgfmathtruncatemacro{\FBC@numrows}{\pgfplotsretval-1}%
  \foreach \FBC@i in {0,...,\FBC@numrows}{%
    \pgfplotstablegetelem{\FBC@i}{category}\of\accuracytable%
    \edef\FBC@cat{\pgfplotsretval}%
    \def\FBC@target{#1}%
    \ifx\FBC@cat\FBC@target
      \pgfplotstablegetelem{\FBC@i}{model_key}\of\accuracytable%
      \edef\FBC@row{\pgfplotsretval}%
      \foreach \FBC@col in {#2}{%
        \pgfplotstablegetelem{\FBC@i}{\FBC@col}\of\accuracytable%
        \edef\FBC@val{\pgfplotsretval}%
        \xdef\FBC@row{\FBC@row\noexpand&\noexpand\pgfmathprintnumber[fixed,fixed zerofill,precision=3]{\FBC@val}}%
      }%
      \xdef\FBC@accum{\FBC@accum\FBC@row\noexpand\\}%
    \fi
  }%
  \FBC@accum
}
\makeatother
